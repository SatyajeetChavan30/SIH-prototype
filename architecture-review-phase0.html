🔴 Friction Points (Shallow Modules)

1. Presentation Logic Dominates Root

Problem: build_ppt.py and check_ppt.py occupy the root alongside where Phase 0 skeleton should go. No jalraksha/ package exists yet.

Why it matters: A developer cloning the repo sees presentation scripts first, not the solver. The interface (what's visible at root) is as complex as the implementation (only 2 files, but they're 750 and 177 lines of dense PowerPoint logic).

Deletion test: If you deleted build_ppt.py, the core system would still work. It's not a load-bearing module.

2. No Package Structure Yet

Problem: There's no jalraksha/ package directory, no jalraksha/cli/, no jalraksha/solver/. The prototype specs and literature are loose .md files in root.

Why it matters: Nowhere to put Phase 0 code (CLI, cache, DEM fetch). New developers won't know where to start implementing.

3. Documentation Scattered

Problem: CLAUDE.md, literature.md, prototype specs.md, docs/RESEARCH-FINDINGS.md, docs/DEEP-RESEARCH-PROMPT.md — all at different levels.

Why it matters: No single source of truth for phase definitions, constraints, or data sources. Hard to keep in sync.

4. No Configuration Story

Problem: build_ppt.py hardcodes paths (template location, output path). Phase 0 needs a configuration system (where to cache DEMs, API keys, demo dam, etc.) but none exists.

Why it matters: Hard to parameterize Phase 1–4. Every phase will re-invent config handling.

5. No Test Co-Location

Problem: No tests/ directory. The `/verify-jalraksha` skill exists but has nowhere to live in the codebase.

Why it matters: Analytical tests (Ritter, Stoker, Thacker) need to be importable by Phase 1 solver. Right now they have no home.

🎯 Top Recommendation: STRONG

Deepen Phase 0 by extracting presentation concerns into a separate tools/sih-presentation/ module and scaffolding the core jalraksha/ package.

This makes Phase 0 itself deep: a single entry point to a well-organized data pipeline, with presentation tooling clearly separated.

Candidate 3: Create CONTEXT.md Domain Glossary

Worth Exploring
Problem: Domain vocabulary is spread across CLAUDE.md, literature.md, prototype specs, and undocumented in code. Terms like "Tier-1", "lake-at-rest", "Manning's n", "breach hydrograph" have no single definition.
Solution: Create CONTEXT.md as a living glossary: 
# JalRaksha Domain Glossary

## Hydrodynamics
- **Lake-at-rest:** Zero-velocity condition over arbitrary bathymetry; test of hydrostatic balance
- **Manning's n:** Friction coefficient (s/m^1/3); inferred from land cover
- **HLLC flux:** Riemann solver with transverse-momentum correction

## Geometry
- **Metric CRS:** EPSG:32643 or equivalent UTM (never degrees)
- **30m DEM:** Copernicus GLO-30 resolution; indicative only, not survey-grade
- **Ter-1/2/3:** CWC screening framework; Tier-1 = rapid without survey

## Validation
- **Ritter test:** Dry-bed dam-break; exact solution for correctness gating
- **Chamoli 2021:** Real event; published <5% travel-time benchmark

## Data Sources (Approved)
- Copernicus DEM (free, COG)
- Google Open Buildings (CC BY 4.0)
- CWC NRLD/NRSD (public)

## Data Sources (Forbidden)
- India-WRIS, Bhuvan, CartoDEM (geo-fenced / login-gated)
Benefits:
  • Locality: Single source of truth for domain terms
  • Leverage: Code comments can reference CONTEXT.md; reduces redundancy
  • Communication: New team members understand domain without reading all research
  • Maintainability: Update glossary once, everywhere reflects it
Note: CONTEXT.md is lazy-created during grilling (first time a term needs clarification). Not blocking for Phase 0, but recommend starting it.

🤔 Why This Architecture?

These deepenings follow the deep modules principle:

  • High functionality, simple interface: Phase 0 will have ~500 lines of CLI + cache + DEM logic, but from the user's perspective it's one command: jalraksha run --dam tehri
  • One responsible module per concern: Presentation is separated from solver. Solver is separated from export. SPH is separated from SWE.
  • Testable in isolation: Tests can import jalraksha.solver without loading the React dashboard (Phase 10).
  • Supports the 18-phase plan: Each phase can build on earlier ones without circular dependencies.
